

Markdown高亮实现方案


Assistant:
这是一个很好的技术问题。用户正在Flutter中实现一个Markdown阅读器，想要添加文本高亮功能，需要持久化，且高亮可以跨段落。

让我从第一性原理来分析这个问题：

1. 本质问题：如何在一个会被解析和渲染的文档中，稳定地标记一段文本的位置

2. 核心挑战：
   - Markdown → AST → Widget 的转换链
   - 选中的文本跨越多个AST节点
   - 需要持久化（意味着需要某种稳定的定位方式）
   - 文档可能会变化（但用户说不考虑修改的鲁棒性）

3. 常见方案：

方案1：基于原始文本偏移量 (start, end)
- 简单直接
- 问题：Markdown渲染后的文本与原始文本不同（去掉了标记符号）
- 需要维护原始偏移量到渲染偏移量的映射

方案2：基于渲染后文本的偏移量
- 从用户选择获取
- 问题：需要反向映射回AST节点进行高亮渲染

方案3：基于XPath类似的路径定位
- 类似Web Annotation标准
- 记录：节点路径 + 节点内偏移量
- 更结构化

方案4：文本锚点（Text Anchor）
- 记录选中文本本身 + 前后文上下文


- 更鲁棒，类似Hypothesis使用的方式

方案5：修改Markdown源文件
- 插入特殊标记如 ==高亮文本==
- 破坏性，但最直接

实际应用中，Hypothesis（Web注释工具）采用Range、TextQuote和TextPosition的组合方案；Kindle等阅读器通常用位置百分比配合文本锚点；Notion等编辑器则依赖块级ID加块内偏移。

对于Flutter Markdown的高亮需求，考虑到修改的鲁棒性、性能优先和跨节点支持，我倾向于采用AST节点路径加偏移量的方案。具体做法是解析Markdown生成AST后，为每个叶子节点分配稳定的路径索引，高亮数据记录为(startNodePath, startOffset, endNodePath, endOffset)的形式，渲染时遍历AST检查文本节点是否在范围内，然后分割并应用样式。这种方法在AST解析后需要建立节点索引映射，能够有效处理跨节点的高亮场景。

Markdown 高亮功能的本质分析

第一性原理拆解

用户选择 → 定位标识 → 持久化存储 → 重新渲染时还原
     ↓
  核心问题：如何建立一个【稳定的定位锚点系统】

本质上，你需要解决的是 两个坐标系的映射问题：

┌─────────────────────────────────────────────────────────┐
│  坐标系A: 用户看到的渲染结果（Flutter Widget树）          │
│  坐标系B: 你能持久化的东西（Markdown源文本 / AST）        │
└─────────────────────────────────────────────────────────┘

主流方案对比

| 方案 | 原理 | 跨节点 | 性能 | 稳定性 |
|------|------|--------|------|--------|
| 原始文本偏移 | (start, end) 基于 Markdown 源码 | ✅ | ⭐⭐⭐ | ❌ 编辑即失效 |
| 渲染文本偏移 | (start, end) 基于纯文本化后的内容 | ✅ | ⭐⭐⭐ | ❌ 映射复杂 |
| 文本锚点 | 存储 prefix + text + suffix | ✅ | ⭐⭐ | ⭐⭐ 模糊匹配 |
| AST路径+偏移 | (nodePath, offset) 结构化定位 | ✅ | ⭐⭐⭐ | ⭐⭐⭐ |
| 修改源文档 | 插入 ==高亮== 语法 | ✅ | ⭐⭐⭐ | ⭐⭐⭐ |

推荐方案：叶子节点线性索引 + 偏移量

既然你说 不考虑修改的鲁棒性，追求极致性能，这个方案最合适：

核心思想

Markdown AST 的所有【叶子文本节点】可以拉平成一个线性序列

Hello World           ┌─────────────────────────────┐
                        │ LeafNode[0]: "Hello World"  │
This is bold text   │ LeafNode[1]: "This is "     │
                        │ LeafNode[2]: "bold"         │  ← AST叶子节点序列
                        │ LeafNode[3]: " text"        │
Quote here            │ LeafNode[4]: "Quote here"   │
                        └─────────────────────────────┘

// 1. 解析时构建索引
class MarkdownHighlightIndex {
  final List leaves = [];
  final Map nodeToLeafRange = {};
  
  void buildFrom(AstNode root) {
    _traverse(root);
  }
  
  void _traverse(AstNode node) {
    if (node.isLeafText) {
      nodeToLeafRange[node] = (leaves.length, leaves.length + 1);
      leaves.add(node as LeafTextNode);
    } else {
      final startIdx = leaves.length;
      for (final child in node.children) {
        _traverse(child);
      }
      nodeToLeafRange[node] = (startIdx, leaves.length);
    }
  }
}

// 2. 渲染时应用高亮
InlineSpan buildSpanWithHighlight(
  LeafTextNode node,
  int leafIndex,
  List highlights,
) {
  final text = node.text;
  final cuts = {0, text.length};
  
  // 找出所有切割点
  for (final h in highlights) {
    if (h.startLeafIndex == leafIndex) cuts.add(h.startOffset);
    if (h.endLeafIndex == leafIndex) cuts.add(h.endOffset);
  }
  
  final sortedCuts = cuts.toList()..sort();
  
  // 分割并标记
  return TextSpan(
    children: [
      for (int i = 0; i < sortedCuts.length - 1; i++)
        TextSpan(
          text: text.substring(sortedCuts[i], sortedCuts[i + 1]),
          style: _isHighlighted(leafIndex, sortedCuts[i], highlights)
              ? highlightStyle
              : normalStyle,
        ),
    ],
  );
}

难点2：跨节点渲染

选区跨越: [Node1 的后半段] + [Node2 全部] + [Node3 的前半段]
           ^^^^^^^^^^^^^^^^   ^^^^^^^^^^   ^^^^^^^^^^^^^^^^
              部分高亮          全部高亮        部分高亮

遍历到每个节点时独立判断即可，复杂度 O(nodes × highlights)，可用区间树优化到 O(nodes × log(highlights))。

// ============ 数据结构 ============
class Highlight {
  String id;
  
  // 主要定位方式
  TextAnchor anchor;
  
  // 缓存（性能优化）
  CachedPosition? cache;
  
  // 元数据
  String color;
  DateTime createdAt;
}

class CachedPosition {
  int startOffset;      // 纯文本偏移
  int endOffset;
  String contentHash;   // 用于失效检测
}

// ============ 核心实现 ============
class PerformantHighlightManager {
  // 渲染产物
  String _plainText = '';
  List _astMapping = [];
  String _contentHash = '';
  
  // 高亮数据
  List _highlights = [];
  
  // 1. 渲染阶段：构建索引
  void onMarkdownRendered(MarkdownAST ast) {
    _plainText = '';
    _astMapping.clear();
    
    _traverseAST(ast, (node, text, range) {
      _astMapping.add(TextSpanMapping(
        node: node,
        start: _plainText.length,
        end: _plainText.length + text.length,
      ));
      _plainText += text;
    });
    
    _contentHash = _computeHash(_plainText);
    
    // 快速路径：检查缓存
    _resolveHighlights();
  }
  
  // 2. 还原高亮（两阶段）
  void _resolveHighlights() {
    for (var highlight in _highlights) {
      Range? range;
      
      // 阶段1: 尝试缓存（O(1)）
      if (highlight.cache?.contentHash == _contentHash) {
        range = Range(
          highlight.cache!.startOffset,
          highlight.cache!.endOffset
        );
        if (_validateRange(range, highlight.anchor.exact)) {
          _applyHighlight(range, highlight);
          continue;
        }
      }
      
      // 阶段2: 模糊搜索（O(n)）
      range = _fuzzySearch(highlight.anchor);
      if (range != null) {
        // 更新缓存
        highlight.cache = CachedPosition(
          startOffset: range.start,
          endOffset: range.end,
          contentHash: _contentHash,
        );
        _applyHighlight(range, highlight);
      }
    }
  }
  
  // 3. 模糊搜索算法（容错性）
  Range? _fuzzySearch(TextAnchor anchor) {
    // 精确匹配
    int pos = _plainText.indexOf(anchor.exact);
    if (pos >= 0 && _validateContext(pos, anchor)) {
      return Range(pos, pos + anchor.exact.length);
    }
    
    // 前缀+后缀定位
    List candidates = _findByContext(anchor.prefix, anchor.suffix);
    if (candidates.isNotEmpty) {
      return Range(candidates[0], candidates[0] + anchor.exact.length);
    }
    
    // 模糊匹配（处理轻微变化）
    return _fuzzyMatch(anchor.exact, threshold: 0.9);
  }
  
  // 4. 应用高亮到渲染树
  void _applyHighlight(Range range, Highlight highlight) {
    // 找到range对应的AST节点
    List affectedNodes = _astMapping.where(
      (m) => m.overlaps(range)
    ).toList();
    
    for (var mapping in affectedNodes) {
      // 分割TextSpan并插入高亮样式
      _injectHighlightStyle(mapping, range, highlight.color);
    }
  }
}

// ============ 优化技巧 ============
class TextSpanMapping {
  MarkdownNode node;
  int start;
  int end;
  
  // 预计算的区间树（快速范围查询）
  IntervalTreeNode? intervalNode;
  
  bool overlaps(Range range) {
    return !(range.end = end);
  }
}

// ============ 核心组件 ============
class HighlightableMarkdown extends StatefulWidget {
  final String data;
  final List highlights;
  final Function(Highlight)? onHighlightCreated;
  
  const HighlightableMarkdown({
    Key? key,
    required this.data,
    required this.highlights,
    this.onHighlightCreated,
  }) : super(key: key);

  @override
  State createState() => _HighlightableMarkdownState();
}

class _HighlightableMarkdownState extends State {
  String _plainText = '';
  String _contentHash = '';
  
  @override
  void initState() {
    super.initState();
    _buildPlainText();
  }
  
  @override
  void didUpdateWidget(HighlightableMarkdown oldWidget) {
    super.didUpdateWidget(oldWidget);
    if (oldWidget.data != widget.data) {
      _buildPlainText();
    }
  }
  
  void _buildPlainText() {
    // 简化：移除Markdown标记，提取纯文本
    _plainText = _stripMarkdown(widget.data);
    _contentHash = md5.convert(utf8.encode(_plainText)).toString();
  }
  
  String _stripMarkdown(String markdown) {
    // 简单实现，生产环境应该遍历AST
    return markdown
        .replaceAll(RegExp(r'[#*_`\[\!]'), '')
        .replaceAll(RegExp(r'\n+'), ' ');
  }
  
  void _handleTextSelection(TextSelection selection) {
    if (selection.isCollapsed) return;
    
    final selectedText = _plainText.substring(
      selection.start,
      selection.end,
    );
    
    final anchor = TextAnchor(
      exact: selectedText,
      prefix: _plainText.substring(
        (selection.start - 20).clamp(0, _plainText.length),
        selection.start,
      ),
      suffix: _plainText.substring(
        selection.end,
        (selection.end + 20).clamp(0, _plainText.length),
      ),
    );
    
    final highlight = Highlight(
      id: DateTime.now().millisecondsSinceEpoch.toString(),
      anchor: anchor,
    );
    
    widget.onHighlightCreated?.call(highlight);
  }
  
  @override
  Widget build(BuildContext context) {
    return SelectableText.rich(
      _buildHighlightedText(),
      onSelectionChanged: (selection, cause) {
        if (cause == SelectionChangedCause.longPress) {
          _handleTextSelection(selection);
        }
      },
    );
  }
  
  TextSpan _buildHighlightedText() {
    final List segments = [];
    
    // 初始化：整个文本无高亮
    segments.add(_TextSegment(0, _plainText.length, null));
    
    // 应用每个高亮
    for (var highlight in widget.highlights) {
      final range = _resolveHighlight(highlight);
      if (range != null) {
        segments.addAll(_splitSegments(segments, range, highlight));
      }
    }
    
    // 构建TextSpan
    return TextSpan(
      children: segments.map((seg) {
        return TextSpan(
          text: _plainText.substring(seg.start, seg.end),
          style: seg.highlight != null
              ? TextStyle(backgroundColor: seg.highlight!.color)
              : null,
        );
      }).toList(),
    );
  }
  
  Range? _resolveHighlight(Highlight highlight) {
    // 尝试缓存
    if (highlight.cachedHash == _contentHash &&
        highlight.cachedStart != null &&
        highlight.cachedEnd != null) {
      return Range(highlight.cachedStart!, highlight.cachedEnd!);
    }
    
    // 模糊搜索
    final anchor = highlight.anchor;
    int pos = _plainText.indexOf(anchor.exact);
    
    if (pos >= 0) {
      // 验证上下文
      final actualPrefix = _plainText.substring(
        (pos - 20).clamp(0, _plainText.length),
        pos,
      );
      if (actualPrefix.endsWith(anchor.prefix)) {
        highlight.cachedStart = pos;
        highlight.cachedEnd = pos + anchor.exact.length;
        highlight.cachedHash = _contentHash;
        return Range(pos, pos + anchor.exact.length);
      }
    }
    
    return null;
  }
  
  List _splitSegments(
    List segments,
    Range range,
    Highlight highlight,
  ) {
    // 简化实现：实际需要处理区间合并
    return segments;
  }
}

这是一个非常经典且极具挑战性的工程问题，特别是在 Flutter 这种自绘引擎下处理富文本（Markdown）的高亮。

你现在的混乱是因为你在“渲染层（View）”和“数据层（Model）”之间反复横跳，试图用一种简单的方法解决两个层面的问题。

让我们从第一性原理出发来拆解这个问题。

第一性原理：什么是“高亮”？

本质上，高亮就是给一段特定的文本范围（Range）附加一个特定的样式（Style）。

在 Markdown 阅读器的语境下，这个过程涉及三个坐标系：
原始 Markdown 文本坐标系（纯字符串索引，0 到 length）。
解析后的 AST（抽象语法树）坐标系（节点树结构）。
渲染后的 RenderObject 坐标系（屏幕上的像素位置或 TextSpan 树）。

核心矛盾在于：
用户是在渲染层（RenderObject）进行选择，而你需要将这个选择映射回数据层（Markdown 文本或 AST）进行持久化；下次打开时，又要从数据层准确映射回渲染层。

社区常见实践方案分析

通常有三种主流思路，按照你的需求（跨段落、持久化、高性能），我们可以逐一评估：

方案一：基于原始文本索引 (Raw Text Indexing) - 你尝试过的
原理：记录 start 和 end 索引（例如：第 100 个字符到第 150 个字符）。
优点：持久化数据极小，逻辑看起来简单。
致命缺陷：
    Markdown 语法干扰：Markdown 源码中包含 `, , # 等不可见或格式化字符。用户选中的是渲染后的 "Hello"，但源码可能是 He**llo`。索引很难一一对应。
    跨节点困难：如果 Markdown 解析器（如 flutter_markdown）将文本拆分成了多个 Widget（例如 Paragraph + Image + Paragraph），单纯的文本索引很难映射到具体的 Widget 树中。

方案二：基于 DOM/Widget 树修改 (AST Injection) - 破坏结构
原理：在解析 Markdown 生成 AST 后，直接修改 AST，把 `` 节点插入到树中。
优点：渲染极其稳定，因为高亮变成了内容的一部分。
致命缺陷：
    脏数据：你修改了原文或 AST，这使得“高亮”和“原文”耦合了。如果原文更新了，高亮位置可能会错乱。
    跨段落噩梦：Markdown 的 AST 通常是块级（Block）优先的。如果你高亮了“段落 A 的后半段 + 段落 B 的前半段”，你需要在 AST 中强行拆分节点，这在技术上非常复杂且容易出错。

方案三：基于渲染层的装饰器模式 (Render Layer Decoration) - 推荐方向
原理：不修改 Markdown 原文，也不修改 AST 结构。而是在渲染阶段，根据“定位锚点”，动态地给 TextSpan 增加背景色。

针对你的需求（Flutter + 跨段落 + 极致性能）的最佳实践路径

考虑到你要跨各种 AST 节点且追求极致性能，我建议采用 “虚拟层叠加” 或 “TextSpan 重构” 的方案。

核心思路：将高亮视为“元数据 (Metadata)”，而非“内容 (Content)”

步骤 1：定义持久化的锚点 (The Anchor)

不要只存 start/end 索引。为了鲁棒性，你需要存“指纹”。
一个高亮对象应该包含：
class HighlightMarker {
  final String startPath; // 比如 "paragraph[3]/text[0]" (DOM 路径)
  final int startOffset;  // 节点内的偏移量
  final String endPath;
  final int endOffset;
  final String textContent; // 选中的纯文本（用于校验，防止原文修改后错位）
}
在 Flutter Markdown 中，这很难直接获取，通常我们退而求其次，使用 *纯文本内容的相对偏移量，但必须是剔除 Markdown 符号后的纯文本*的偏移量。

步骤 2：渲染时的“TextSpan 重写” (The Re-write)

这是实现跨段落、高性能的关键。

Flutter 的 Markdown 渲染流程通常是：
Markdown String -> AST Nodes -> Widget Builders -> TextSpans -> RichText Widgets。

你需要介入 Widget Builders -> TextSpans 这个环节。

具体算法（假设你使用 flutter_markdown 或类似库）：

预处理（建立映射表）：
    在 Markdown 解析为 AST 后，遍历 AST，计算出每个 AST 节点对应的“纯文本全局索引范围”。
    节点 A (Paragraph): 纯文本索引 0-50
    节点 B (List): 纯文本索引 51-100
    这个过程非常快（O(n)），可以在后台线程做。

命中检测（Intersection）：
    当你有一个高亮范围（比如纯文本索引 40-60）时，你计算它与 AST 节点的交集。
    节点 A (0-50): 与 40-60 的交集是 [40, 50]。 -> 该节点需要部分高亮。
    节点 B (51-100): 与 40-60 的交集是 [51, 60]。 -> 该节点需要部分高亮。

构建 TextSpan（最关键的一步）：
    自定义 Markdown 的 ElementBuilder。当构建节点 A 时，你不再直接返回一个 TextSpan(text: "...")。
    而是根据第 2 步的计算结果，将节点 A 的文本切分为三段：
    TextSpan(text: "前40个字")
    TextSpan(text: "第40-50个字", style: 这里的背景色是黄色)
    TextSpan(text: "剩余...")

为什么这个方案符合你的要求？

跨段落：因为我们将一个跨段落的高亮（40-60）拆解成了两个独立的渲染任务（节点 A 渲染 40-50，节点 B 渲染 51-60）。视觉上它们是连在一起的。
跨 AST 节点：同理，无论是加粗、斜体还是列表，只要它最终被渲染为 Text，它就有纯文本索引，就可以被计算交集。
高性能：
    没有复杂的 DOM 操作。
    计算纯文本索引和交集是纯数学运算，极快。
    Flutter 的 TextSpan 树构建非常高效。
持久化：你只需要存储“纯文本的 start/end”。虽然原文修改会导致错位，但配合 textContent 校验，可以做简单的容错（比如提示用户高亮失效）。

Flutter 具体落地难点与黑科技

在 Flutter 中实现这个方案，最大的痛点是：如何获取 Markdown 渲染后的纯文本索引？

flutter_markdown 并没有直接暴露这个映射。你可能需要做以下 hack：

自定义 Builder：
    继承 MarkdownElementBuilder。
全局计数器：
    维护一个全局的 currentTextIndex。
    Markdown 解析是线性的。每当你 visitElement 并准备渲染 Text 时，你知道当前的 text.length。
    记录：当前节点对应 [currentTextIndex, currentTextIndex + text.length]。
    累加：currentTextIndex += text.length。
样式注入：
    在 visitElement 中，检查当前范围是否在高亮列表中。如果是，返回切割并加了背景色的 RichText。

总结

不要试图去修改 Markdown 文本，也不要试图通过复杂的 Widget 树去定位。

第一性原理方案：
抽象：将 Markdown 视为一条连续的、剔除了格式符号的“纯文本流”。
映射：建立 AST 节点到这段“纯文本流”的坐标映射。
切片：将用户的高亮范围（Range）切片分配给各个 AST 节点。
渲染：每个 AST 节点只负责渲染自己分到的那部分高亮。

这就是目前富文本编辑器（如 ProseMirror, Slate.js）以及高性能阅读器处理高亮的通用逻辑（Decorations）。在 Flutter 中，利用 TextSpan 的组合能力，这完全是可行的。

这是一个非常经典且具有挑战性的问题。在 Markdown 阅读器中实现“持久化、跨段落、高性能”的高亮，本质上是在处理“非结构化数据（Markdown 源码）”与“结构化渲染树（AST/Widget Tree）”之间的映射关系。

从第一性原理出发，我们来拆解并重构你的思路。

一、 第一性原理：高亮的本质是什么？

从本质上讲，高亮是在一个有序的字符序列上，标记一个 (start, end) 的区间，并给这个区间赋予额外的视觉属性。

但在 Markdown 场景下，复杂性在于：
多层表现形式：源码层（Raw Text） -> 语法树层（AST） -> 渲染层（Flutter Widgets/TextSpans）。
偏移量不一致：源码中的 bold 在渲染层只显示 bold，源码索引和渲染索引是对不上的。
跨越性：一个高亮可能跨越加粗、链接、甚至多个段落（多个 AST 节点）。

二、 社区主流方案与思路

1. 基于 DOM 的路径偏移法 (类似 Web Range API)
这是浏览器实现高亮的逻辑。它不记录全局索引，而是记录：
startContainer: 起始节点在树中的路径（如：第2个段落下的第1个加粗节点）。
startOffset: 该节点内的文字偏移量。
endContainer / endOffset: 结束节点信息。

优点：非常稳定，不受其他段落变化影响。
缺点：在 Flutter 中，Widget 树是易失的，你需要自己维护一套持久化的 AST 节点索引系统。

2. 线性可见文本映射法 (Linear Visible Index) —— 推荐方案
这是处理编辑器高亮最常用的高性能方案。

核心思路：
建立映射表：在解析 Markdown 生成 AST 时，同时生成一个“可见字符流”。
双向索引：记录每一个“可见字符”在“源码”中的位置。
    可见文本：Hello world
    源码：Hello world
    映射：可见索引 0 对应源码索引 2。
持久化：只存储可见文本的起始和结束偏移量。

三、 极致性能的实现方案（Flutter 场景）

如果你追求极致性能，且不考虑修改鲁棒性（即文档内容不变），建议采用 “平铺式可见文本偏移量 + 渲染拦截” 的方案。

第一步：AST 节点的唯一标识化
在解析 Markdown 时，给每个 AST 节点分配一个自增的 nodeIndex。
class HighlightRange {
  final int startNodeIdx;
  final int startOffset;
  final int endNodeIdx;
  final int endOffset;
}

第二步：构建“虚拟线性坐标系”
不要直接操作 Widget，而是在解析 Markdown 得到 AST 后，遍历 AST 提取出所有的 TextNode。
将所有 TextNode 的文字拼接成一个虚拟的“长字符串”。
记录每个 TextNode 在这个长字符串中的起始位置。
高亮存储：存储在这个“虚拟长字符串”中的 start 和 end 索引。

第三步：渲染层的“切片”算法 (The Slicing Strategy)
这是性能的关键。在 Flutter 构建 RichText (TextSpan) 时，不要等渲染完了再去覆盖层画高亮，而是在构建 TextSpan 的过程中进行拆分。

逻辑如下：
当你要渲染一个 AST 节点（比如一个加粗节点 TextSpan(text: "Hello")）时：
计算该节点在“虚拟长字符串”中的范围 [nodeStart, nodeEnd]。
检查是否有高亮区间与此范围有交集。
如果有交集，将这个 TextSpan 拆分为多段：
    TextSpan(text: "He", style: normal)
    TextSpan(text: "ll", style: highlightStyle)
    TextSpan(text: "o", style: normal)

为什么这样快？
无额外 Overlay：高亮就是 TextSpan 的一部分，利用 Flutter 原生的渲染引擎，性能最高。
按需计算：只在 build 阶段计算一次。

四、 如何处理跨段落？

跨段落的本质是：高亮区间覆盖了多个 AST 节点。

使用上述的“渲染层切片”算法，跨段落自然就解决了：
高亮区间是 [10, 100]。
段落 A 范围是 [0, 50] -> 渲染时截取 [10, 50] 部分高亮。
段落 B 范围是 [51, 150] -> 渲染时截取 [51, 100] 部分高亮。
中间的节点自动会被全量高亮。

五、 总结建议

针对你的需求，建议的架构如下：

存储层（持久化）：
    存储 (startOffset, endOffset)。这里的 Offset 是全篇文档纯文本（忽略 Markdown 标记）的绝对索引。
    为什么？ 因为这样最鲁棒。即使你把 ** 改成 __，纯文本索引依然是不变的。

逻辑层（映射）：
    在 Markdown 解析器（如 dart_markdown）遍历 AST 时，累加当前已处理的纯文本长度，从而确定每个 AST 节点对应的“纯文本区间”。

渲染层（注入）：
    自定义 Flutter Markdown 的 Builder。在生成 TextSpan 的地方，根据当前节点的纯文本区间与高亮区间做 intersect（交集）计算，动态拆分 TextSpan。

避坑指南：
不要尝试破坏 Markdown 结构：在源码里插入 `` 标签会破坏原有的语法解析（比如破坏了表格或代码块）。
不要使用系统选择回传的索引直接存储：系统选择的索引通常是基于 RenderBox 的，滚动后或重新加载后会失效。必须转换成基于内容的索引。
性能瓶颈：如果高亮非常多（成千上万个），在 build 阶段进行区间重叠计算会变慢。此时可以使用 区间树 (Interval Tree) 来加速查找哪些高亮命中了当前节点。

这种方案是目前市面上高性能阅读器（如微信读书、各种代码编辑器）处理高亮/装饰的主流思路。

4) 你要的“跨段落 + 跨 AST 节点 + 极致性能”：路线

路线 1（性能上限最高）：文本不变，单独绘制高亮层（overlay painting）
核心思想：不要为了高亮去拆 TextSpan；TextSpan 树尽量稳定。高亮只是画一堆矩形。

做法（关键 API 都是 Flutter 官方的）：

1) 把要高亮的内容最终落到某个 RenderParagraph（通常是 RichText 产物）  
2) 对每个高亮区间 \start,end)，用 RenderParagraph.getBoxesForSelection(TextSelection(...)) 拿到这个区间在屏幕上的 box 列表 ([api.flutter.dev)  
3) 在文字背后画这些 rect（CustomPainter / RenderObject 里画都都行）

为什么它快：文本布局（layout）是最重的；这条路线让 layout 结果复用，只在 paint 阶段叠加矩形。  
为什么它跨段落/跨节点强：只要你的“文档坐标系”是同一个字符流，跨多少节点都只是 offset 区间而已。

super_text_layout 的存在本质上就是在补齐 Flutter 对“基于文本布局的自定义装饰绘制”的能力缺口（它就明确说用来画 selections/highlights/carets） (GitHub)。

你需要注意的坑：
你必须保证 offset 对应的字符流和 RenderParagraph 实际布局的字符流一致（包括换行、空格折叠、软换行、列表符号、WidgetSpan 占位等）。
WidgetSpan 通常会占用一个“字符位置”（概念上类似 object replacement char），你要定义：高亮跨过它时要不要画背景（通常不画，只在文本 box 上画即可）。
高亮很多段时：把 ranges 做 合并/归一化（interval set），避免重复计算 boxes。

路线 2（更直观但更重）：在构建 TextSpan 时切分并加 background
渲染时遍历叶子文本节点（leaf spans），给每个节点一个全局 \a,b) 范围；与高亮 ranges 求交集，必要时把该 leaf 切成 1~3 段：

非高亮段：原 style
高亮段：原 style + backgroundColor（或自定义 Paint）

优点：不用额外 painter，逻辑直观。  
缺点：高亮变化会导致 span 树变化，build 成本更高；大量高亮/大文档时不如 overlay。

5) 实战建议：我会怎么给你定方案（贴合你描述的约束）

你说“跨各种 AST 节点的稳定性和鲁棒性，不考虑修改鲁棒性，考虑极致性能”，那我建议：

1) 定义 canonical 文档字符流（这是成败关键）
AST 遍历时生成一个线性的“文本流”，block 之间你明确插入 \n 或 \n\n（取决于你渲染视觉与选择体验）
WidgetSpan 统一用一个占位符计数（长度=1）
任何“渲染时新增的字符”（比如列表的 • 、引用的 > ）要么也进入 canonical，要么你就别让它参与 selection/highlight（两者必须一致）

2) 持久化存储用全局 offset range
Highlight { int start; int end; }（排序、合并）
（可选）再加一个 context（前后各 N 个字符）用于你未来想做“轻微文本变化也能找回”的增强，但你当前不要求也可以不做

3) 渲染层用 overlay painting + getBoxesForSelection
文本布局一次，多高亮只是多画几个 rect
把 boxes 结果按 layout 宽度/滚动偏移做缓存（layout 变了就清）

4) 如果你现在的 markdown renderer 是“多 widget 拼起来的”
想要“跨段落选中 + 跨段落高亮”会明显更麻烦（你得把全局 range 切到每个 block，再对每个 RenderParagraph 分别 getBoxes）  
能改结构的话，尽量让“可选择区域”更统一。Flutter 也建议用 SelectionArea/SelectableRegion 来做子树选择 ([Flutter API Docs)，但你要的持久化 offset通常还是自己维护一套 canonical mapping 更踏实。

6) 你现在的“混乱”怎么落地成下一步（最小可行路径）
如果你只做一条主线，我建议按这个顺序推进：

先让 markdown → canonical plain text 可复现（同一份输入，永远同一份输出）
让一次 selection 能得到 canonical 的 \[start,end)（哪怕先只支持纯文本段落）
用 overlay 把这段画出来（哪怕先只支持单段）
再逐个补：链接、粗体、代码、列表、引用、跨段落、WidgetSpan……

只要第 1 步做好，后面都是可控的增量工程。
